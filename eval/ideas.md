# Ideas

Hypotheses not yet tried, best first. Each cites evidence from a run. Mark the one being measured **(running)**, and delete an entry once its experiment is committed; git keeps the record.

- **(running in lane a)** **Ashby rejects automated submissions as spam.** Run 20261004-221244-2 (Qumulo) filled the whole form in under 4 minutes, then Ashby's invisible reCAPTCHA v3 answered "flagged as possible spam ... please submit your application again". The agent ran the solver, which skips v3, and stopped. First try: on that message, wait a minute and submit again, within the 3-attempt limit. If it keeps failing: get a v3 token from CapSolver (`ReCaptchaV3EnterpriseTaskProxyLess` or `ReCaptchaV3TaskProxyLess`, with the page's site key and action) and make the page's `grecaptcha.execute` return it. From Ashby's bundle: the form calls `grecaptcha.enterprise.execute(key, {action: "job_apply"})` when the org has Enterprise enabled (plain `grecaptcha` otherwise), using `recaptchaPublicSiteKey`, or `recaptchaUniversalPublicSiteKey` behind a feature flag; both keys are in the page's inline config. It sends the token prefixed with `ENT===` (or `UNIVERSAL_ENT===`). The loaded `/recaptcha/enterprise.js?render=<key>` (or `api.js`) script shows which applies. A generic version: replace `execute` with a function that records `{key, action}` and returns a promise, which `jobs captcha` resolves with CapSolver's token.
- **Click snapshots carry screenshots nobody looks at.** In run 20261004-221243-0 (GM, Workday), every click took a fresh `get_window_state` (56 calls, 2.4 s each, 134 s) and then the `click` itself (49 calls, 2.7 s each, 133 s): a third of the run's first 13 minutes. `get_window_state` returns a full screenshot by default, and its docs call `include_screenshot: false` "the cheap path when you're just re-indexing before an element ax action"; `query` also narrows the tree to matching rows. The prompt's click recipe passes neither. Add both to the recipe. Measured on a Finder window: the default call took 1.8 s and returned 915 KB; with `include_screenshot: false`, 1.1 s and 32 KB with every token; adding `query` cut it to 3 KB. Separately, tokens stay valid until the window's next snapshot, so several clicks on one unchanged page could share a snapshot.
- **Greenhouse dropdowns pick the wrong option.** Run 20261004-221243-1 (DoorDash, Greenhouse) spent turns 7–18 (104 s to 738 s, about 11 minutes) on dropdowns: typing a filter and pressing return chose the wrong School and Degree, which the agent then had to clear and redo. Try: after typing the filter, read the open listbox and choose the option whose text matches exactly (the profile's `school_dropdown_names` lists accepted spellings) instead of pressing return on the first match. Run 20261004-222500-5 (Glean) repeated it: "School and degree need fixing" at 310 s, fixed by 431 s.
- **Greenhouse's 8-box security code.** In run 20261004-222500-5 (Glean), the emailed code went into 8 separate one-character boxes; typing key by key misaligned them, and re-entering took from 579 s past 683 s. One-time-code widgets usually spread a pasted code across their boxes: try `browser_type` with the whole code into the first box in the default `insert_text` mode.
- **Email codes start with a search for Gmail.** In the same run, Greenhouse's emailed security code took turns 22–29 (2.3 minutes), starting with "Checking for a Gmail tool". Give step 4 the exact Gmail call to search for the newest code.
- **The skills rule clears pre-filled skills.** In run 20261004-213528-0 (Workday), turns 25–29 removed 9 skills Workday had pre-filled, because the prompt says skills pickers "stay empty". Reword it: never add skills, and leave whatever the site filled in.
- **Page rereads while waiting.** In the first 6 minutes of run 20261004-213528-0, `get_browser_state` ran 58 times at 3.1 s each, about half the agent's time, mostly rereading while a page loaded. Try waiting once for the page to change, or check whether cua-driver can read the page without a screenshot when the agent needs only refs.
- **Workday error after the resume upload.** Run 20261004-213528-0 showed "Something went wrong" after Autofill with Resume (turn 15) and recovered with a refresh. Find what triggers it: the upload method or its timing.
